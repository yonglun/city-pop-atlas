# 采集审核工作流

## 线上使用

打开网站“采集审核”，对照当前值与候选值，点击来源核对，再批准或填写理由后拒绝。首批队列包含2个真实来源冲突，尚未替用户作出决定。批准保存到独立校订层，刷新与资料重新导入后保留。所有导入候选先为pending，不会直接修改正式展示。

“字段覆盖”仍是事实断言，不是确切事实的保证；审核者应核实原始来源与版本对应关系。原始专辑日期与再版日期不能混用。

## 文件格式

```json
{"candidates":[{"entityId":"album_mignonne","field":"releaseDate","value":"1978-09-25","sourceUrl":"https://www.110107.com/s/oto/page/onuki_RCA?ima=5504","sourceType":"official label","checkedAt":"2026-10-02","note":"与艺人官网的9月21日存在冲突，请核查。"}]}
```

单次最多50项、64KiB。只接受属性定义中存在的字段、有限标量/数组值、HTTPS证据URL与真实日历日期。请求不会自动抓取提交的URL。

## 从采集器转换

```sh
python3 scripts/prepare_review.py --input collected-candidates.json --catalog data/catalog.json --output review-ready.json
```

转换器只生成待审字段。测试fixtures不能冒充已抓取证据。MusicBrainz release的发行日期只有在目标是edition时才会进入队列，不会覆盖album概念的首次发行日。媒体链接、曲目关系及新实体仍需独立策展后再发布。

## 本地测试

```sh
LOCAL_REVIEW=1 npm run dev
```

开发服务只绑定127.0.0.1，忽略调用者伪造的身份头；显式开启时注入本地测试身份。该模拟只在开发服务，未打包到Worker。默认本地模式只读。

## 安全边界

生产审核依赖已验证的“仅站点所有者可访问”平台边界。必须配置SITE_REVIEW_MODE=owner-private和精确SITE_REVIEW_ORIGIN，同时要求平台转发的登录用户ID、同源JSON POST和来源检查。只有服务访问凭据而没有浏览器用户身份的请求不能审核。

这是当前私人站点的审核机制，不是公开站点的编辑权限系统。**在扩大Site访问范围之前，必须先把审核模式设为disabled并发布生效，或实现经过验证的所有者ID授权。** 不得只改分享设置后仍保持现有审核模式。模式开关本身不实时查询分享状态。

源码默认不包含启用审核的运行配置、用户ID或秘密。审核决定/覆盖值/历史只保存在D1，不提交公开GitHub。

## 撤销校订（v0.5）

在“已批准”候选或最近审核记录中，找到仍然生效的批准，点击“撤销校订”。确认将恢复的值，填写原因，再点击“确认撤销”；取消不会修改数据。撤销后候选回到待审核，保留原批准和撤销两条历史，可重新核查后再次批准。

- 只允许撤销当前仍然生效的那次批准。若同一字段先后批准A、B，需先撤销B，才能撤销A
- 恢复原值同时恢复原来源、原校订者对应候选和原时间；原先没有校订层时移除覆盖，回到基础资料
- 若该实体的基础资料或生效校订已经变化，服务器拒绝撤销，避免覆盖较新的资料。即使基础实体只修改了其他字段，也会要求重新核对
- 本功能上线前的批准没有恢复快照，因此不提供撤销按钮；后续新批准可以撤销并完整恢复这些旧校订
- 最近历史只展示100条，但仍可从“已批准”候选撤销更早的生效校订
- 重复请求只记录一次撤销；撤销目标固定为原批准记录，不会误撤销后来重新批准的结果
- 撤销必须使用与批准相同的私有站点登录身份、同源JSON和权限检查。快照、审核理由和历史不提交GitHub

新表approval_snapshots由增量迁移创建，原有数据和历史保留。API为POST /api/review/undo/{approval-event-id}，请求包含expectedVersion与非空note。旧批准不通过猜测回填快照。


## v0.9 候选批次预览与去重

选择 JSON 文件后先调用 `/api/review/preview`，不会写入候选、批准层或审核历史。首次打开空库仍会按现有规则初始化基础资料。界面逐行展示实体/属性、当前值、候选值、来源 URL、来源类型、采集日期和备注；提供新增、已有候选（含其决定状态）、与当前值相同、批内重复、无效五类结果。取消不会导入；必须明确点击“加入待审核队列”。

- 接受候选数组或带 `candidates` 数组的对象，兼容 `prepare_review.py` 输出。每批1–50项，文件与请求体均最多64KiB；包裹字段也计入请求字节数。
- 任一候选无效会阻止整批导入。修正文件后重新预览。来源仅接受无用户名/密码的 HTTPS URL；不会主动抓取该 URL，也不代表来源已获核实。
- 去重键为实体、属性、值、来源 URL 与来源类型；采集日期和备注不参与。数组值按原顺序比较，URL 按输入字符串精确比较，不推测不同来源、别名或实体是否相同。
- 重复采集不会覆盖原候选的来源日期/备注，也不会重新打开已批准/拒绝项。已有旧版 ID 按语义识别，不更改历史 ID。已有历史重复项不会合并或删除。
- 确认时服务端再次读取现状、验证并去重，稳定候选 ID 与原子插入防止并发重复。统计展示实际新增和跳过数量；新候选始终为 pending。预览期间现状变化可能影响最终数量，审批仍有独立版本/基础值冲突保护。
- 不创建新实体，不自动合并关系，不自动批准，不启用定时采集。现有所有者私有访问与 CSRF 边界保持不变。

## 审核数量与筛选

采集审核顶部的「待审核总计」汇总字段校订与结构变更两个完整队列；另列各队列的待审核数量，以及跨队列的已批准、已拒绝和全部数量。两类候选是不同任务，不按实体去重。字段状态筛选只影响字段校订列表；结构状态和类型筛选只影响结构变更列表。结构状态选项中的数量按当前类型计算。筛选不会改变顶部总计。

两个队列都成功读取后才显示总计。初次加载、刷新、提交审核以及任一队列读取失败期间，未确认的数量显示「—」，不会当作零。失败时保留已读取的另一队列；若显示上次读取的列表，会明确提示数量尚待刷新确认。顶部「刷新全部队列」会重新核验管理员权限并重读两个队列。

回归测试 `tests/ui-review-counts.cjs` 覆盖字段待审核0、结构待审核54、已批准2/全部56，三语、两个加载顺序、两类部分失败、重试、筛选作用域、空队列及权限撤销后迟到响应。所有修改只涉及界面数量和加载状态，不改候选状态、批准逻辑或服务器管理员名单。
